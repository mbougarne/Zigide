# Research: Local Git Hooks and CI Are Separate Gates

A repository can version a hook without activating it in every clone. Git chooses its hook directory from `core.hooksPath`; when that setting is absent, Git uses the repository's default hooks directory under `.git/hooks`. Git does not automatically use a project folder such as `.githooks/`. Consequently, a checked-in `.githooks/pre-commit` file runs only after the clone's Git configuration points to that directory. A setup target such as `zig build hooks` can make that local configuration change.

The local hook and hosted CI are independent:

- The pre-commit hook runs synchronously for a local commit only when installed and executable. A later setup cannot retroactively gate a past commit.
- A CI workflow runs only for events selected by its trigger configuration. A `push` restricted to `main` does not cover pushes to feature branches, while a matching `pull_request` event can run separately.
- An AI review workflow failure does not establish whether a build/check workflow ran; inspect the failed job and the CI workflow's triggers.

The practical debugging sequence is to inspect `core.hooksPath`, check for the active hook at Git's resolved path, read the repository's setup instructions, then inspect CI triggers and the actual failed job name.
