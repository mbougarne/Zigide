# Research: How Repository Orientation Constrains Agent Work

## Epistemic Boundary

This record describes observable repository evidence and a small educational model. It does not claim access to private model attention, logits, hidden states, parameters, or reasoning.

## Observable Orientation Pipeline

```text
agent rules -> project vision -> architecture contracts -> milestone evidence -> ticket execution
```

The reading order is useful because each layer narrows the next action. `agents/` defines traceability and honesty requirements; the root and architecture documents define product intent and boundaries; the tickets turn those boundaries into independently verifiable work.

## Toy Constraint Model

The following values are human-authored teaching labels, not model embeddings:

| Repository layer | Main question answered | Example constraint |
| --- | --- | --- |
| Agent rules | How should work be recorded and verified? | Never claim an unrun test |
| Architecture | What boundaries must implementation preserve? | Domain does not import UI |
| Roadmap | What evidence completes a phase? | Milestone 0 needs a UI decision |
| Ticket | What is the smallest verifiable unit? | Acceptance criteria and dependencies |

## Project Shape Learned

Zigide is intentionally small and Zig-first: one main application with explicit modules, a single mutable-state owner, background workers that return versioned results, ports/adapters for external concerns, LSP/ZLS for language features, and framed out-of-process extensions. Local persistence emphasizes atomic writes and recovery. The first release is a macOS arm64 Zig work loop rather than VS Code compatibility.

## What This Record Can and Cannot Teach

It can teach why repository orientation should proceed from governance to architecture to executable work units, and why acceptance criteria turn broad goals into evidence. It cannot show the actual internal computation of an AI agent or prove implementation behavior that has not yet been built and tested.
