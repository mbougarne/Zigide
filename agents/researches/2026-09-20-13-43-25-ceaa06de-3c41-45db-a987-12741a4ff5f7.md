# Research: Enforcing Zig Module Boundaries Through Build Imports

## Explicit Import Tables

In Zig's build API, each module has a named import table. `@import("name")` is available only when the build graph maps that name into the importing module. Keeping these mappings explicit provides a compiler-enforced boundary: a domain root cannot name an adapter module that the build has not granted.

The graph is directional and non-transitive. If module A imports B and B imports C, A does not automatically receive a direct import named C. A module should declare only its direct requirements.

## Negative Compile Tests

A useful boundary test compiles an intentionally invalid fixture using the same import allowlist as the real module. The test is successful only when compilation fails with the expected missing-module diagnostic. If the prohibited edge is later granted, the diagnostic changes and the test fails. This mutation was exercised for the `foundation -> ui` edge in this interaction.

## Scope of the Current Roots

ZIT-003 through ZIT-007 establish module roots and build structure without introducing product service APIs. Later implementation tickets can add behavior to these roots while preserving the named import contract. Passing these architecture tests does not establish that later services or the overall Milestone 0 user journey exist.
