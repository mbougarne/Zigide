# Research: Why Recording Only "Real Work" Biases the Ledger

## Epistemic Boundary

The proportions below are mocked for teaching. The observable fact is the rule change in the source conversation: records are now created for every prompt, not only repository-changing ones.

## Selection Bias, Applied to This Repository

Selection bias is the distortion that appears when the rule for *including* data correlates with the thing the data is supposed to measure. The old recording rule — "record prompts that change the repository" — had exactly this shape. The ledger's purpose is to show how human-AI collaboration works; but collaboration includes steering, correction, disagreement, and clarification, which frequently change no file. Under the old rule those prompts vanished.

A mock session shows the distortion. Suppose ten prompts produce (invented proportions):

| Prompt kind | Count | Changes files? | Old rule records it? |
| --- | ---: | --- | --- |
| Build a feature | 3 | yes | yes |
| Fix after feedback | 2 | yes | yes |
| Feedback that redirects the agent | 3 | no | **no** |
| Question about a decision | 2 | no | **no** |

The recorded history shows five action prompts and zero steering prompts — a reader would conclude the human mostly issued build orders and the agent mostly succeeded. The actual session was half steering. The dataset is not wrong anywhere, yet it lies in aggregate. This is the same mechanism as survivorship bias — the famous armor-the-bombers example, where analysts initially studied only planes that returned — inclusion correlated with outcome.

## The Same Bias in AI Training and Evaluation

This is not only a bookkeeping concern. Datasets used to train and evaluate models suffer identically: if human-AI transcripts are kept only when the task succeeded or produced an artifact, models learn from a world where correction rarely happens, and evaluations overestimate autonomy. Complete traces — including reversals, misreadings, and "you over-generalized that precedent" moments — are the rarer and more valuable data. This repository's records-for-every-prompt rule makes it, deliberately, that rarer kind of dataset.

## Cost, Honestly Stated

Removing the bias is not free: every prompt now carries record-writing overhead, and this project has already flagged process weight as a risk. The mitigation is unchanged — tooling validates records mechanically (`zig build check` already enforces ledger consistency), and record length should scale with interaction weight: a short prompt may earn a short record, but never zero record.

## What This Record Can and Cannot Teach

It can teach what selection bias is, how an innocent-sounding inclusion rule produced it, and why completeness beats curation for a collaboration case study. It cannot quantify the bias in this project's actual history (the unrecorded prompts are, by definition, not fully recoverable), and the table's proportions are invented.

## Suggested Learning Experiments

* Count the recorded prompts so far by kind (action versus steering) before and after this rule; watch the steering share rise.
* Pick any public dataset you know and write down its inclusion rule; ask what the rule correlates with.
* Revisit the process-weight open item after twenty more records and decide, with evidence, whether record length needs a convention.
