# Research: What a Command Inventory Reveals About an Agent

## Epistemic Boundary

The frequency table below is mocked for teaching. The observable facts are this interaction's actual command record and the conversation it links.

## The Agent Loop, Seen Through Its Commands

A coding agent alternates between predicting text and acting through tools:

```text
observe context -> choose an action -> run a tool -> read the result -> repeat -> answer
```

The language model half of this loop is probabilistic and private. The tool half is neither: every command is an observable, reproducible event. That asymmetry is why this repository's records lean on tool activity — commands are the part of an agent's behavior that can be audited without any access to model internals.

The new `agents/commands/` convention deliberately keeps only the *set* of commands, not the sequence or outputs. That is a lossy compression chosen for a purpose: the set answers "what tools does this kind of work require?", which is the learning question, while sequence and outputs already live in conversation records and Git history where they are needed for auditing.

## Sets Versus Frequencies

A mock example of what the compression keeps and discards. Suppose an interaction ran (mock counts):

| Command | Runs |
| --- | ---: |
| `git status` | 4 |
| `zig build check` | 3 |
| `grep` | 2 |
| `uuidgen` | 1 |

The inventory keeps only the four names. Frequencies would tell you about the agent's *process* (four `git status` runs suggest state-checking after every mutation — a caution signal, or a healthy habit). The set tells you about the *task* (this work needed version-control inspection, a build system, text search, and identity generation). Both are legitimate signals; the repository chose the task view, and the choice is itself documented so a future maintainer can revisit it with evidence.

## A Vocabulary Grows Like a Curve

Command inventories across many prompts behave like vocabulary acquisition: early records introduce many new commands, later ones mostly repeat the established toolkit. In mock terms, if record `k` introduces `new(k)` previously unseen commands, a healthy project shows `new(k)` decaying toward zero except when the work genuinely changes phase — the way this interaction introduced no new Zig commands but the first UI-spike record likely will introduce several. Watching where the curve jumps is a cheap way to spot phase changes in the project's history without reading every record.

## What This Record Can and Cannot Teach

It can teach the observable/private split in agent behavior, what a set-based trace preserves versus a frequency- or sequence-based one, and why lossy records should state what they discard. It cannot recover the discarded frequencies for past interactions, and the counts above are invented.

## Suggested Learning Experiments

* After ten command records exist, compute the new-commands-per-record curve and mark where it jumps.
* Compare one command record against its conversation's evidence section: everything in the inventory should be inferable from the conversation, but not vice versa — verify the direction of that implication.
* Design the alternative record you would want for the frequency view, and decide what it would cost to maintain honestly.
