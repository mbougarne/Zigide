# Research: Explicit Composition and Stable Lookup

## Observable Design

The application context is an ordinary Zig struct. Its constructor receives the allocator and two borrowed interfaces, then constructs a registry and logger. The executable chooses adapters; the test chooses a deterministic clock and capture sink. No service-discovery graph or runtime container is needed.

A registry owns copied keys because callers may reuse stack buffers immediately after registration. It borrows callback contexts because application services own those lifetimes. Returning a handler value avoids retaining a pointer into hash-map storage, which can move when registrations grow. This does not extend the callback context lifetime; the documented caller contract still matters.

Registration checks the namespace syntax and duplicate identity before allocation. If copying the ID or growing the map fails, cleanup releases the new owned bytes and existing commands remain resolvable. Exhaustive allocation-failure injection verifies each allocation boundary rather than relying only on the successful path.

## Reproducible Behavioral Examples

Register `zigide.file.open`, `zigide.file.close`, and `example.run-task_2` in all six possible orders. Resolve each name and invoke its callback a distinct number of times. The observed counts must depend on the names, never registration order. Register the same name twice with different contexts: the second call must fail and the original callback must remain reachable.

Register a name using a mutable buffer, overwrite that buffer, grow the map with 100 additional names, then use both the original lookup result and the last registration. These are direct lifetime tests. The integration fixture also advances manual time and verifies the logged timestamp without sleeping or reading the OS clock.

## Limits and Model Claims

These are observable code and test facts, not captured model internals. No attention weights, logits, private reasoning, or hidden activations were available or inferred. Passing tests support the covered contracts; they do not establish future argument validation, concurrent registration disposal, process supervision, or GUI behavior. The existing framework-free boundary leaves those later tickets explicit.
