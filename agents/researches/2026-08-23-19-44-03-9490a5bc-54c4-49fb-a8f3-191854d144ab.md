# Research: How an Agent Over-Generalizes a Precedent

## Epistemic Boundary

The analysis explains the observable mistake using general properties of language models. It does not claim access to the internal computation that produced the mistake; the similarity framing below is a teaching model, not a trace.

## The Mistake, Precisely

Earlier in the project, one precedent was established: *a merged draft record, discovered before commit, may be replaced with correct per-prompt records.* Later, the agent faced a different situation — staged conversation records missing a research link — and applied an edit, reasoning "staged, therefore amendable." The maintainer's correction shows the precedent had a narrower shape: it licensed **replacing a wrong record wholesale before publication**, not **incrementally editing records that were correct for their moment**.

## Why Models Generalize This Way

A language model applies past patterns by similarity, not by rule inference. Both situations share salient surface features — "staged, not committed", "record file", "fixing an omission" — and differ in a subtler one: whether the original record was *wrong about its moment* (the merged record was) or *correct but later incomplete* (the frontmatter was). Similarity-driven generalization keys on the shared features and can miss the distinguishing one, especially when the distinguishing feature is a concept the repository had not yet written down anywhere.

A useful mock illustration (invented weights): score the analogy by counting matched features.

| Feature | Merged-record case | Frontmatter case |
| --- | --- | --- |
| Uncommitted | yes | yes |
| Record file | yes | yes |
| Repairing a defect | yes | yes |
| Record wrong about its own moment | yes | **no** |

Three of four features match. A similarity engine that weighs all features near-equally endorses the analogy; only elevated weight on the fourth feature blocks it. Humans learn such feature weights from being corrected — which is exactly what happened here, and why the correction is more valuable written down than merely obeyed once.

## The General Defense: Make the Boundary Explicit

The remedy applied in this project is the systematic one: after the correction, the rule "record files are write-once from creation" was written into the governing documents and the agent's persistent memory. An explicit rule removes the need for correctly-weighted analogy — the next decision is a lookup, not a generalization. This mirrors a broader engineering principle already active in this repository: conventions survive when they are written and checked, not when they are inferred.

## What This Record Can and Cannot Teach

It can teach that analogy-based generalization fails on under-weighted distinguishing features, that corrections are most valuable when converted into explicit rules, and that a public mistakes-and-fixes trail is evidence, not embarrassment. It cannot show the actual internal representation of the flawed analogy; the feature table is a human-authored reconstruction.

## Suggested Learning Experiments

* Find another precedent in this repository's records and write down its licensing conditions explicitly; check whether a plausible-but-wrong extension exists.
* When reviewing agent work, ask "which written rule permits this?" — an unanswerable case is either a rule gap or an over-generalization in progress.
* Compare this record with the earlier instruction-ambiguity research note: ambiguity resolves at parse time, over-generalization at precedent-application time; both are fixed by writing the resolution down.
