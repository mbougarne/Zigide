# Research: Why the Backlog Had to Be Corrected — Ambiguity and Repair

Backfill note: this research record was written retroactively under the mandatory-research policy, for an interaction conducted by a different agent (GitHub Copilot). It analyzes that interaction's observable record; it does not claim access to the other agent's internals. The `created_at` matches the record stem for pairing.

## Epistemic Boundary

The mock interpretation table below is human-authored for teaching. The observable facts are in the source conversation: the correction prompt, the 35-to-216 restructuring, and the audit that caught a dependency cycle.

## One Sentence, Several Valid Structures

The original instruction contained the phrase "each feature or epic should has it own file with its own ticket". At least two readings are grammatically defensible:

| Reading | Resulting layout | What happened |
| --- | --- | --- |
| One file per *ticket* | 35 files, each one ticket | First implementation chose this |
| One file per *feature*, holding its tickets | 35 files, 216 tickets grouped | What the maintainer meant |

A language model resolves ambiguity by producing whichever completion its training makes most probable in context — conceptually, choosing among readings weighted by learned plausibility, not by asking the speaker. There is no internal "I noticed two readings" unless the model surfaces the ambiguity in its output. This is why prompt ambiguity is not a user failure: natural language legitimately underdetermines structure, and the resolution mechanism is statistical, not clarifying by default.

## The Second Signal: Calibration

The correction also said "I don't think that the project will be done in 35 tickets." This is a different error class — not parsing but **granularity calibration**. "A ticket" has no intrinsic size; the first pass anchored on the roadmap's ~35 deliverable bullets, while the maintainer's mental unit was "independently reviewable change". The repaired convention (files are work packages, tickets are small verifiable units) encodes the calibration *in the repository*, so the next agent inherits it instead of re-guessing. That is the general remedy: turn resolved ambiguity into written convention.

## Repair Loops Beat First-Try Perfection

The observable sequence was: generate → maintainer reviews → correction prompt → regenerate → audit → fix the cycle the audit found → re-audit. Two properties made this cheap:

1. The wrong draft was **uncommitted**, so replacing it was a pre-publication correction, not history rewriting — the same ledger rule this repository applies to trace records.
2. The audits were **deterministic programs**, so the second attempt was verified the same way as the first, and the dependency cycle between two release tickets was caught mechanically, not by rereading 216 entries.

A toy way to see why review-then-repair outperforms hoping for a perfect first try, with mock numbers: if a first attempt is fully right with probability `0.5`, one review-and-repair round with an effective validator lifts the outcome toward the validator's coverage, not the generator's odds. The validator, not the generator, becomes the reliability floor.

## What This Record Can and Cannot Teach

It can teach that ambiguity resolution in models is probabilistic, that granularity expectations must be written down to persist, and that deterministic validators are what make regeneration safe. It cannot identify which tokens or internal states led to the first misreading, and the probability figures are illustrative only.

## Suggested Learning Experiments

* Rewrite the original instruction so only the intended reading survives; compare its length to the ambiguous version — precision costs words.
* Pick any Zigide ticket and ask whether a stranger could verify it independently; if not, it is a work package, not a ticket.
* Give the same ambiguous sentence to two different assistants and compare the chosen readings — an observable, reproducible ambiguity experiment that needs no model internals.
