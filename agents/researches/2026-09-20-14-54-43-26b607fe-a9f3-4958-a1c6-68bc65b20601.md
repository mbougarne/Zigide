# Research: Application Layer vs. Composition Root

These names describe different architectural responsibilities:

- The **application layer** implements product use cases and orchestrates domain services. It is reusable from multiple entry points, such as a UI, command-line interface, or tests.
- The **composition root** is the executable's outermost setup point. It selects and connects concrete adapters, application services, and UI, then starts the program. It should not contain reusable product workflows.

In Zigide's direct-import graph, `ui` may import `application`; `application` imports core modules and ports; adapters implement ports; and `composition` imports `application`, `adapters`, and `ui`. That makes the composition root depend outward while keeping reusable application services independent of startup and concrete presentation.

Calling these modules `application` and `app` technically encoded the split but required readers to infer it. Naming the outer boundary `composition` makes the distinction visible in paths and `@import` names. This is a naming clarification, not a change to the accepted modular architecture.
