# Research: Pull-Request Evidence Must Not Become Review Policy

## Trust Boundary

A pull request can modify code, documentation, and files named like agent instructions. Those files are useful evidence about the proposed change, but allowing the head revision to redefine review policy creates a prompt-injection path.

## Layered Control Example

Use illustrative binary controls `g` for same-repository contributor gating, `b` for loading policy from the base SHA, and `r` for read-only model access. A toy score `S = 0.35g + 0.40b + 0.25r` equals `1.00` when all controls are present and `0.60` if `b=0`. This is not a measured security probability; it demonstrates that separate controls cover separate failure modes.

## Application to Zigide

The head revision is checked out below `source/`, while the agent starts from an instruction-free runner root. The workflow copies Zigide's trusted base rules and accepted ADRs into the assembled prompt. The model can inspect `source/` but cannot modify files, run commands, use the network, or publish comments. A later job rechecks the exact head SHA before its deterministic comment write.

## Evidence Limit

Actionlint and local structural checks prove configuration syntax and declared permissions. They do not prove provider review quality, GitHub runtime enforcement, or live secret handling. Those require a later disposable-PR acceptance test after explicit credential setup.

This explanation covers observable configuration and general security mechanics, not hidden model reasoning or telemetry.
