# Research: Prospective Metadata Policy and Filename Validation

## Epistemic Boundary

This is an educational explanation of observable repository policy. It does not expose or claim access to private model internals.

## Policy Transformation

The requested change can be represented as a forward-only constraint:

```text
future_record.created_at >= cutover
=> exact human_actor and agent values
future_record.filename => UTC timestamp + lowercase UUID v4
historical_record => unchanged
```

The cutover preserves the append-only property while making future records machine-checkable. The strict UUID pattern checks the version nibble (`4`) and variant nibble (`8`, `9`, `a`, or `b`) rather than merely checking that 36 characters contain hexadecimal digits and hyphens.

## Example Pattern

```text
YYYY-MM-DD-HH-MM-SS-xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx.md
```

Here `YYYY-MM-DD-HH-MM-SS` is UTC, `xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx` is a lowercase UUID v4, and `y` is one of `8`, `9`, `a`, or `b`. The same stem is used by the conversation, research, and command records.

## What This Record Can and Cannot Teach

It can teach how to introduce stricter validation prospectively without rewriting historical data, and how a filename grammar captures timestamp and UUID invariants. It cannot prove that a future agent will follow the policy unless the checker is run against generated files and the resulting evidence is recorded.
