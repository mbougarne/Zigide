# Research: When a Proxy Counter Is Not the Budget

Automated safeguards often compare a measured value with a configured budget. That comparison is valid only when both values measure the same unit.

Here, `--max-turns 20` limits agentic API rounds. The action's post-run guard instead compared that limit with `result.num_turns`, which includes the initial prompt and tool-result messages. One assistant round can issue several parallel reads, producing several tool results while consuming only one API round.

For an illustrative trace, suppose 16 assistant rounds contain 8 single-tool rounds and 8 rounds with two parallel reads. The result-message count can be `1 initial prompt + 8 * 1 + 8 * 2 = 25`, even though the model used only 16 of its 20 permitted API rounds. Comparing `25 > 20` creates a false failure. These values illustrate the documented counter semantics; they are not captured hidden model state.

Raising the configured limit would make the incorrect comparison less likely, but it would also enlarge the real API-round and cost budget. A safer temporary adapter keeps the real limit at 20, tolerates the wrapper step's false post-hoc failure, and independently validates the execution envelope. The downstream gate accepts only `subtype: success`, `is_error: false`, bounded non-empty text. Therefore a genuine `error_max_turns`, authentication failure, missing log, or malformed output still fails the job.

The durable fix belongs upstream: compare the budget with assistant rounds or remove the redundant post-hoc guard because current Claude Code already reports actual limit exhaustion. Until an audited upstream fix is merged and pinned, the local fail-closed adapter preserves both review availability and the intended cost boundary.
