# Text-model spike evidence and recommendation

Evidence for [ZIT-027–033](../../tickets/text-model-spike.md), recorded 2026-10-12.
Verified baseline: remote main `e9903d734b8d824ddd715aca734857cd3242ea8b`;
PR #7 is merged from `01240b87044f7abc11a00d5bb3c911af72a273f8`. No open
PR duplicated this group, and the prerequisite ZIT-004 is already present.

## Recommendation

Retain the original/add-buffer piece table and its single-edit ownership rules as
**the production starting point**, alongside the independent string oracle for
regression testing. The flat descriptor array and full line-index rebuild are
provisional. This spike does not select a permanent storage structure or supply
the versioned document API. No discarded alternate implementation remains.

The index gives much faster lookup, while whole-text rebuilding makes even a
one-byte edit materially slower than copying the contiguous baseline. The table
preserves the original buffer and uses less copying for snapshots; neither fact
establishes faster editing. The retained observations quantify both costs. For
ZIT-044/048, first replace full index rebuilding with affected-line updates; retain
flat pieces while the measured workload stays within the proposed budgets. Move
to an augmented piece tree if longer histories exceed lookup or descriptor-edit
budgets. Introduce an explicit compaction/history policy before claiming bounded
production memory. These are assigned future production tickets, not changes
silently folded into this spike.

| Alternative | Decision and trade-off |
| --- | --- |
| Contiguous string | Retained correctness oracle; very fast memcpy edits at 4 MiB, but scanning line lookup is costly and every edit allocates a document-sized buffer. |
| Flat piece table + line starts | Selected starting point; original bytes and insertion ownership are explicit, snapshots and lookup work, but rebuilding lines dominates edit cost and add history grows without compaction. |
| Augmented piece tree | Deferred fallback for growing piece counts. Expected asymptotic gains are an inference; balancing, allocation failures, and aggregate CRLF/scalar semantics require new measured correctness evidence. |
| Rope | Deferred; not benchmarked here. More nodes, chunk policy, and boundary handling add complexity without a demonstrated need at this workload size. No performance claim is made for it. |

The [reference contract](../../src/text/README.md) specifies UTF-8 rejection,
byte offsets/columns, canonical positions inside terminators, mixed LF/CRLF/CR,
EOF, invalid inputs, copied snapshots, and atomic single-edit failure behavior.
It deliberately leaves UI/LSP conversions and production transactions outside
this scope.

## Hardware, fixture provenance and method

- Apple M3 Pro, model Mac15,6, 11 logical CPUs, 18 GiB RAM; macOS 27.0.1 (26A434).
- Zig 0.16.0, aarch64-macos, ReleaseFast; ordinary Debug/ReleaseSafe checks are separate.
- Fixtures are entirely generated by [the harness](../../tools/text_benchmark.zig)
  from original literal patterns; no user/customer files or third-party corpus.
  Requested sizes round down to complete pattern repetitions.
- Small 4,096 bytes; medium 262,144; large 4,194,304: repeated
  `const a = 123;\r\n`. Long-line 4,194,304: repeated `abcdefghijklmnop` with no
  newline. UTF-8 262,140: repeated `aé😀終\r\n`.
- Open copies and validates generated input in memory, not file I/O. Single-edit
  insert adds `x\r\n` at a middle pattern boundary; delete removes one pattern;
  replace changes one ASCII byte. Snapshot copies the full text. Both lookup
  directions address a middle pattern boundary, before and after fragmentation.
- Each ordinary operation has one unrecorded warmup plus 31 timed observations on
  a freshly opened model. Snapshot hashing and result consumption happen outside
  its allocation/copy interval; setup, deinit, CSV writes and oracle checks are
  outside timed intervals. Each model then receives 1,024 fixed-size replacements:
  one third near the beginning, one third near the end, one third uniformly
  distributed (PRNG seed `0x027033`). Final content is checked against the oracle.
- After fragmentation, 64 cycles insert 4 KiB then delete it at the middle. This
  keeps visible content stable and demonstrates retained deleted insertion history;
  final content is checked again. Churn and sustained edits are separately labeled.
- `std.Io.Clock.awake` elapsed times, nearest-rank p95, median and maximum;
  nanosecond units do not imply nanosecond accuracy. Submicrosecond observations
  may hit timer resolution. These are sequential warm-memory microbenchmarks,
  not cold-start or UI latency measurements. Reference runs before candidate;
  no load isolation, frequency locking or thermal control is claimed. Other work
  on this host may affect outliers, so retain both runs and rerun before budgets
  become release gates.
- A forwarding allocator measures actual requested live and peak bytes, including
  temporary old/new descriptors and indexes. Generated inputs, oracle, CSV and
  final correctness snapshots use an independent allocator. Ordinary timed
  snapshots count in their own peak; sustained/churn peaks are separate histories.
  This is neither RSS nor allocator metadata. Empty/deinitialized models release
  all owned bytes; leak-detecting correctness tests independently verify ownership.

Reproduce from the repository root:

```sh
zig build text-test
zig build check
zig build check -Doptimize=ReleaseSafe
zig build text-benchmark -Doptimize=ReleaseFast -- .zig-cache/text-benchmark.csv
python3 tools/summarize_text_benchmark.py .zig-cache/text-benchmark.csv
```

Local execution uses `-j2` and an isolated `--global-cache-dir` to limit shared
resource contention. The CI job runs ReleaseSafe text checks and uploads raw
ReleaseFast measurements for its exact source head. CI timing is informational:
its hardware is not interchangeable with this target Mac.

## Preliminary acceptance budgets and limits

Propose these release-like storage-only budgets on the recorded target hardware,
with the same 4 MiB fixtures, 31 observations and 1,024 scattered edits:

| Metric | Proposed budget | Spike disposition |
| --- | --- | --- |
| In-memory open p95 | 10 ms | See measured table; file decoding/I/O not included. |
| Insert/delete/replace and sustained edit p95 | 8 ms | Measured prototype passes these workloads; full rebuild still scales with document size. |
| Fragmented forward/inverse lookup p95 | 10 μs | Measured 1,024-edit histories pass; longer histories need remeasurement. |
| Snapshot p95 | 2 ms | Measured copies pass; background snapshot lifetime/version integration is future work. |
| Retained storage after 1,024 edits + churn | 2 × document bytes + 512 KiB | Accounts for index and bounded fixture history; not a bound for unlimited editing. |
| Transient requested-byte peak | 3 × document bytes + 512 KiB | Includes temporary indexes/snapshots within each labeled workload. RSS unmeasured. |

These are **proposed**, not approved release gates or proof that all large files
meet them. Paste/delete churn exposes unbounded history even where this bounded
fixture passes. ZIT-051 must confirm or revise budgets using the production
implementation, longer sessions, realistic files, and representative background
snapshots. No physical-device UI, accessibility, IME, file I/O, undo/versioning,
live-provider or paid-provisioning acceptance belongs to this text-only group.
